# Console 多页面读取性能修复

## 范围与基线

基线 main `8596646`；开发位于独立 CoW 沙盒 `haflow-console-latency-20261015`。用户要求修复运维页及横向检查发现的全部读取瓶颈。仅本地代码交付，未 push、合并、部署或重启当前 8765 服务。

原服务 `fa04788` 实测：HTML 约 6ms，ops API 7.7–14.9s；命名工作流成果 8–11s，白盒 6.27s，任务白盒 3.26s。列表串行等待 overview/project，经验初次打开重复请求；日志显示最后 200 行时完整读入 58MB 文件。

## 修复边界

- 运维 CLI 和 Console 共用一次只读 SQLite 快照，不启动 CLI 子进程或初始化数据库。任务与工作流候选身份按当前创建/重开周期读取；运行探针全进程最多 8 个，未采样保持 unknown。
- Kernel 提取纯 `state_db_path` 解析并沿用现有环境变量优先级；多选择器冲突时列表、详情、成果仍访问同一数据库。
- 项目元数据与现场分开加载，延迟响应同时核对请求序列、项目 ID 和对象身份；列表不等待工位扫描。
- 交付成果复用一个只读 enrichment 事务，使用已有 task 索引读取限量 artifact/PR 回执；文件/Git 核心行为未改。命名工作流的纯成果投影仅 6ms，不能把所有延迟归因于 Git。
- 白盒定向读任务、复用工作流快照与共享 4 并发探测预算；DAG 停滞分析复用配置，避免隐式 StateStore 初始化。仪表板复用同一 inventory 并删除逐工作流重复扫描任务。
- 归档在 SQLite 内筛选、计数、排序和分页，保持 Unicode 子串语义。损坏的非有限时间统一视为 0。
- 日志最多读尾部 256KiB，丢弃开头残行，必要时显示截断；同类刷新合并在途请求，仅保留最新等待范围，旧响应不覆盖新选择。POST 不去重，GET 不持久缓存。
