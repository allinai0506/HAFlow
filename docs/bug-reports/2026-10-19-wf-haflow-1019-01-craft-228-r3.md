## 根因
1. **B1 阻塞安全缺陷（`authenticate_operator` 紧急旁路认证绕过）**:
   - **向量 a（未呈现 token 自动加载导致自比较）**: 原实现在未呈现任何 token 时，自动从 `db_path.parent/credentials`（`server_cred_dir`）按 `{op_clean}_operator.token` 等文件名扫描并读取凭证内容赋给 `presented_token`；随后在解析 `registered_token` 时又从相同同源文件读取，导致 `hmac.compare_digest` 演变成同一文件的自比较。同一 UID 下 worker 只要知道或指定注册的 operator 名称，即可在不呈现任何私钥的情况下通过认证，在 wrapup 阶段绕过 review-closure 校验。
   - **向量 b（operator 名未做路径遍历防护）**: `op_clean = str(operator_id or "").strip()` 未过滤路径分隔符与相对路径，攻击者可通过 `--operator ../clone/evil` 将服务端查找路径引导至 worker 自身克隆目录中的伪造文件，从而实现双读自比较绕过。
2. **B2 测试卫生阻塞项（测试污染生产凭据目录）**:
   - `tests/test_wrapup_review_closure.py` 中的用例直接调用 `state_db.save_user_token(..., db_path=scene.store.db_path)`，但 `state_db._get_credentials_dir()` 未对 `HOME` 做沙盒隔离，硬编码访问 `Path.home() / ".herdr-controller" / "credentials"`，且测试子进程未隔离 `HOME`，导致测试运行期间直接写入宿主真实凭据目录产生 `ops-lead_operator.token` 残留。

## 防复发
1. **显式呈现原则（Presented Token Explicit Requirement）**:
   - 彻底删除 `herdr/review_closure.py` 中自动从服务端目录发现 `presented_token` 的分支代码。`presented_token` 只能来自调用方显式传递（CLI `--operator-token`、`--operator-credentials` 或 `HERDR_OPERATOR_TOKEN` / `HERDR_OPERATOR_CREDENTIALS` 环境变量）。
2. **单一权威源（Single Source of Truth）**:
   - 服务端 `registered_token` 解析折叠至单一权威入口 `state_db.get_user_token(op_clean, "operator", db_path=db_path)`，删除所有冗余的文件扫描与同源 fallback。
3. **输入防御与严格净化（Input Validation & Sanitization）**:
   - 对 `operator_id` 显式检测路径遍历模式（`/`、`\`、`..`），发现立即拒绝。
   - 使用与 `state_db.save_user_token` 一致的正则表达式 `re.sub(r"[^a-zA-Z0-9_\-]", "_", ...)` 执行字符集净化。
4. **测试环境严格隔离（Test Environment Hermetic Isolation）**:
   - 在 `tests/test_wrapup_review_closure.py` 中引入 autouse fixture `isolate_credentials_environment`，将 `HOME` 隔离到临时目录 `test_home`，同时 mock `state_db._get_credentials_dir`。
   - 在测试结束时断言真实 `~/.herdr-controller/credentials` 目录内容保持零新增、零篡改。
5. **对抗性测试门禁**:
   - 补充对抗性用例：服务端存在注册凭证但在无 token 时必须拒绝（向量 a）；路径遍历操作符名必须拒绝（向量 b）；跨 operator 串用 token 必须拒绝；非独立 worker 必须拒绝。
